**Проблеми початкової таблиці:**
- Стовпець `Назва_товару і кількість` містить кілька значень в одній комірці (порушення атомарності).
- Дані про клієнта (`Адреса_клієнта`, `Клієнт`) повторюються у кожному рядку замовлення.
- Відсутня структура зв'язків між сутностями.


## 1. Перша нормальна форма (1НФ)

**Вимоги 1НФ:**
- Кожна комірка містить лише одне (атомарне) значення.
- Кожен стовпець містить значення одного типу.
- Кожен рядок є унікальним.

**Що зроблено:** стовпець `Назва_товару і кількість` розділено на два окремі стовпці — `Назва_товару` та `Кількість`. Кожен товар у замовленні винесено в окремий рядок.

|---|---|---|---|---|---|

## 2. Друга нормальна форма (2НФ)

**Вимоги 2НФ:**
- Таблиця знаходиться в 1НФ.
- Усі неключові атрибути повністю функціонально залежать від усього первинного ключа (немає часткових залежностей).

**Проблема:** при складеному ключі (`Номер_замовлення`, `Назва_товару`) атрибути `Адреса_клієнта`, `Дата_замовлення` та `Клієнт` залежать тільки від частини ключа — `Номер_замовлення`. Це часткова залежність.

**Що зроблено:** таблицю розділено на дві.

## 3. Третя нормальна форма (3НФ)

**Вимоги 3НФ:**
- Таблиця знаходиться в 2НФ.
- Відсутні транзитивні залежності (неключові атрибути не залежать від інших неключових атрибутів).

**Проблема:** у таблиці `Orders` атрибут `Адреса_клієнта` залежить від `Клієнт`, а не напряму від `Номер_замовлення` — тобто `Номер_замовлення → Клієнт → Адреса_клієнта`. Це транзитивна залежність. Аналогічно, `Назва_товару` в `Order_Items` — окрема сутність, яка має зберігатися в окремій таблиці (для уникнення дублювання, якщо з'являться додаткові атрибути товару).

| | customer_id | INT (FK) | Посилання на клієнта |
| **order_items** | id | INT (PK) | Унікальний ідентифікатор позиції |

| | product_id | INT (FK) | Посилання на товар |
| | quantity | INT | Кількість одиниць товару |

### Кардинальності зв'язків

- **Customers → Orders** — один до багатьох (1:N). Один клієнт може мати кілька замовлень; кожне замовлення належить рівно одному клієнту.
- **Orders → Order_Items** — один до багатьох (1:N). Одне замовлення містить одну або більше позицій; кожна позиція належить рівно одному замовленню.
- **Products → Order_Items** — один до багатьох (1:N). Один товар може зустрічатися в багатьох позиціях різних замовлень; кожна позиція посилається на рівно один товар.
- Ефективно зв'язок **Orders ↔ Products** — багато до багатьох (M:N), реалізований через проміжну таблицю `Order_Items`.


## 5. SQL-скрипт для створення таблиць

CREATE DATABASE IF NOT EXISTS mydb
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_unicode_ci;

USE mydb;

-- Таблиця клієнтів
CREATE TABLE customers (
    id       INT AUTO_INCREMENT PRIMARY KEY,
    name     VARCHAR(100) NOT NULL,
    address  VARCHAR(255) NOT NULL
);

-- Таблиця товарів
CREATE TABLE products (
    id    INT AUTO_INCREMENT PRIMARY KEY,
    name  VARCHAR(100) NOT NULL UNIQUE
);

-- Таблиця замовлень
CREATE TABLE orders (
    id           INT AUTO_INCREMENT PRIMARY KEY,
    order_date   DATE NOT NULL,
    customer_id  INT NOT NULL,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT
);

-- Таблиця позицій замовлення (зв'язок M:N між orders та products)
CREATE TABLE order_items (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    order_id    INT NOT NULL,
    product_id  INT NOT NULL,
    quantity    INT NOT NULL CHECK (quantity > 0),
    CONSTRAINT fk_items_order
        FOREIGN KEY (order_id) REFERENCES orders(id)
        ON UPDATE CASCADE
        ON DELETE CASCADE,
    CONSTRAINT fk_items_product
        FOREIGN KEY (product_id) REFERENCES products(id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT,
    CONSTRAINT uq_order_product UNIQUE (order_id, product_id)
);


## Можливі покращення моделі

У межах цього ДЗ збережено вихідну структуру даних з початкової таблиці. Однак у реальній системі модель можна розширити для кращої підтримки бізнес-процесів:

### Розбиття атрибуту `address`

Атрибут `address` у таблиці `customers` можна декомпозувати на окремі поля:

| Атрибут | Тип даних | Опис |
|---|---|---|
| country | VARCHAR(100) | Країна |
| region | VARCHAR(100) | Область / регіон |
| city | VARCHAR(100) | Місто |
| address_line | VARCHAR(255) | Вулиця, будинок, квартира |
| postal_code | VARCHAR(20) | Поштовий індекс |

**Переваги:** валідація адреси, фільтрація замовлень за країною/містом, інтеграція зі службами доставки, коректна побудова звітів за регіонами.

### Розбиття атрибуту `name`

Атрибут `name` можна розділити на:

| Атрибут | Тип даних | Опис |
|---|---|---|
| first_name | VARCHAR(50) | Ім'я |
| last_name | VARCHAR(50) | Прізвище |

**Переваги:** сортування за прізвищем, персоналізоване звертання у листах і повідомленнях, коректна робота з міжнародними іменами.

### Інші можливі розширення

- Додати таблицю `order_status` для відстеження статусу замовлень (новий, оплачений, відправлений, доставлений).
- Винести категорії товарів в окрему таблицю `categories` (зв'язок 1:N з `products`).
- Додати атрибут `price` у `products` та `unit_price` у `order_items` (для збереження ціни на момент замовлення).
- Додати поля `created_at` / `updated_at` для аудиту.
